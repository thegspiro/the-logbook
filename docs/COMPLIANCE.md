# Compliance Hub

The single entry point for compliance questions about The Logbook: which
frameworks the platform aligns with, where each technical control lives in the
code, what remains open, and what deploying departments must do themselves.

**How to use this document:** when adding a control or targeting a new
framework, add a row to the control inventory below and link the evidence
(code path, workflow, or doc). Auditors work from evidence; this table is the
index to it.

Related documents:

- [ISO_STANDARDS_ASSESSMENT.md](./ISO_STANDARDS_ASSESSMENT.md) — full ISO gap
  analysis and prioritized roadmap
- [BACKUP.md](./BACKUP.md) — backup, restore drills, RTO/RPO, DR runbook
- [../SECURITY.md](../SECURITY.md) — security feature reference and
  vulnerability reporting policy
- `docs/module-audit/` — 2026-07 per-module security audit reports

## Framework overview

| Framework                                  | Scope                                        | Status                                                                                                                                                                                                                                       |
| ------------------------------------------ | -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **HIPAA Security Rule**                    | PHI in medical screening, emergency contacts | Deepest alignment — §164.312 controls implemented (password history/age, session timeout, audit retention config, encryption, access control)                                                                                                |
| **ISO/IEC 27001/27002**                    | Information security management              | Strong technical-control coverage; management-system artifacts (policies, risk register, SoA) are the deploying organization's to produce — see assessment                                                                                   |
| **ISO/IEC 29147**                          | Vulnerability disclosure                     | Implemented: `SECURITY.md` policy + RFC 9116 `/.well-known/security.txt` endpoint                                                                                                                                                            |
| **ISO 22301**                              | Business continuity                          | Backup/restore tooling + documented drills and RTO/RPO guidance in BACKUP.md; no HA architecture (single-node deployment model)                                                                                                              |
| **ISO/IEC 27701 / privacy laws**           | PII/PHI data-subject rights                  | Closed 2026-07-31: data export, anonymization, consent tracking, and the public privacy/ToS pages all shipped (see gaps table). Remaining work is the deploying department's — its own retention schedule, notices, and processor agreements |
| **ISO 8601**                               | Date/time interchange                        | Conformant: UTC storage, ISO 8601 wire format, timezone-aware display layer                                                                                                                                                                  |
| **WCAG 2.x / ISO/IEC 40500 / Section 508** | Accessibility                                | Substantial aria coverage, high-contrast mode, tested contrast utilities; axe automation exists but covers little — expansion on the roadmap                                                                                                 |
| **NFPA standards**                         | Fire-service operations                      | Apparatus NFPA compliance tracking (`ApparatusNFPACompliance`); training certifications reference NFPA standards                                                                                                                             |
| **ISO PPC (Insurance Services Office)**    | Fire-insurance grading                       | Readiness scoring and class estimation in the compliance-officer module (`GET /iso-readiness`) — note this "ISO" is unrelated to ISO/IEC standards                                                                                           |

## Segregation of duties — coverage

`assert_different_person` (`backend/app/services/separation_of_duties.py`) is
the single shared control behind ISO 27001 A.5.3. It is deliberately tiny,
raises a `ValueError` subclass so each endpoint's existing
`except ValueError → 400` surfaces it unchanged, and **no-ops when either id is
missing** — an unattributed legacy row cannot be _shown_ to be self-approval,
and failing closed there would wedge pre-existing records.

This table is stated here rather than inferred from the code because the
control's value depends on knowing which paths it does **not** cover. Call
sites were enumerated from the AST, not grepped (app-review A9 pass 3,
2026-10-04).

| Module            | Guarded action                                                                                    | Actor vs. subject                        |
| ----------------- | ------------------------------------------------------------------------------------------------- | ---------------------------------------- |
| Finance           | `approve_step`, `manual_approve`                                                                  | approver vs. the entity's creator        |
| Finance           | `mark_pr_paid`, `mark_expense_paid`, `issue_check`, `waive_dues`                                  | actor vs. requester / submitter / member |
| Storefront        | `record_payment`, `mark_order_paid`, `waive_order_payment`, `refund_order`, `update_order_status` | actor vs. the order's member             |
| Admin hours       | approve, bulk approve (unless the department sets `admin_hours.allow_self_approval`, see below)   | approver vs. the entry's owner           |
| Training          | manual `review_submission`                                                                        | reviewer vs. submitter                   |
| Skills testing    | examine, validate, void, return                                                                   | examiner vs. candidate                   |
| Meeting minutes   | approve                                                                                           | approver vs. submitter                   |
| Driver exceptions | approve (checked twice: against the requester **and** the exception's subject)                    | reviewer vs. requester / subject         |

**Deliberately not guarded**, each for a stated reason — this half is the part
worth keeping current:

| Path                                         | Why not                                                                                                                                                                                                                                                                            |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Denial / rejection / withdrawal, everywhere  | Declining or withdrawing your _own_ record is not a conflict of interest. Only the approving direction is gated.                                                                                                                                                                   |
| `void_check`, `unwaive_dues`                 | Reversals, and neither takes an actor parameter. Voiding your own check or re-imposing your own waived dues moves money _away_ from the actor.                                                                                                                                     |
| `mark_pr_ordered`, `mark_pr_received`        | Procurement status transitions, not disbursements; no actor parameter.                                                                                                                                                                                                             |
| `approve_by_token` (external email approver) | The approver has no Logbook account to compare an id against. The equivalent conflict is enforced by address instead: a step whose `approver_value` is the requester's own email is refused unless that step sets `allow_self_approval`.                                           |
| Training auto-approve (`create_submission`)  | The auto-approve branch creates a credited record with **no reviewer at all**, so an actor≠subject test has nothing to compare. Bounded by configuration instead — see TR-5.                                                                                                       |
| Admin hours, `allow_self_approval` on        | A department with one officer who reviews admin hours has no second person to send an entry to. The switch is off by default and writable only under `settings.manage`, not `admin_hours.manage`; a self-approval still records `approved_by == user_id`, so it is visible as one. |
| `record_dues_payment`                        | **Open, not by design** — see OPS-8 in [KNOWN_LIMITATIONS.md](./KNOWN_LIMITATIONS.md). Its storefront analogue and its own sibling `waive_dues` are both guarded.                                                                                                                  |

Separately: none of the guarded money paths requires a _distinct_ permission,
so this is self-dealing prevention rather than three-way separation — the
requester can still execute a payment somebody else approved. A
`finance.disburse` / treasury tier remains an open owner decision (FIN-4).

## What the software cannot do for you

Deploying departments own the management-system side of every framework:

- **HIPAA:** sign BAAs with hosting/email/SMS vendors; run workforce training;
  maintain sanction and incident-response policies; breach notification has
  **statutory deadlines** (60 days for HHS/individual notice) — put them in
  your SOPs.
- **ISO 27001:** policies, risk assessment, Statement of Applicability,
  internal audits, management review. The control inventory above is your
  evidence index, not your ISMS. Pre-filled skeletons for the policy set
  and SoA live in [policies/](./policies/) — replace the
  `[DEPARTMENT: ...]` placeholders and adopt them formally.
- **Key custody:** offline storage of `ENCRYPTION_KEY`/`ENCRYPTION_SALT` and
  friends — see [BACKUP.md](./BACKUP.md).
- **Records retention schedules:** statutory retention for fire-service
  records varies by state; keep your schedule in department SOPs until the
  configurable retention engine ships.
- **Physical and personnel security** at the station and for any self-hosted
  hardware.
